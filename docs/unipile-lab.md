# Private Unipile preview lab

This is a fixture-first experiment, isolated from onboarding and public profile claims. It uses the Unipile **v1** contract only. The panel at `/unipile-lab` and browser API at `/api/unipile-lab` return 404 unless `UNLINKED_UNIPILE_TEST_ENABLED=true`, a Supabase browser session is valid, and its user ID appears in `UNLINKED_UNIPILE_TEST_USER_IDS` (comma-separated). There is no agent-key access. The provider callback at `/api/unipile-lab/callback` is also disabled by the feature flag, but authenticates with the pending state and secret token described below rather than browser cookies.

## Tester usage

Sign in with an existing allowlisted Unlinked test user, then open `/unipile-lab` on the configured test stage.

- **Connect my LinkedIn:** Choose **Start Hosted Auth** and complete any provider login or challenge yourself. Refresh the panel if verification is still pending after returning. A verified callback shows a basic own-profile preview; **Show up to 10 of my connections** makes the separate own-connections request. **Reconnect my source** verifies the existing source again. In the default fixture mode, Hosted Auth is synthetic and cannot complete a real connection.
- **Preview a profile:** Paste a plain HTTPS `linkedin.com/in/<slug>` or `www.linkedin.com/in/<slug>` URL without query parameters or fragments, then choose **Preview through demo account**. Live targets must be approved in the configured slug list. The result is marked **Viewed through the demo account**. Only **Check visible connections** requests the target's viewer-visible connections; it never substitutes the demo viewer's own network. This URL is lookup input, not an ownership claim or a new sign-in method.
- **Outcomes and clearing:** `empty` means the requested page returned no people; `partial` means more results may exist beyond the bounded page. `denied`, `unavailable`, and `unsupported` are displayed as errors rather than empty networks. **Clear preview** clears the current preview, not the linked source. Repeated reads reuse the current preview until it expires or is cleared; no next page is fetched. Results are private previews, with no profile import, relationship write, publication, or Unlinked sync.

## Stage configuration and contracts

The default transport is synthetic. Set `UNLINKED_UNIPILE_TEST_MODE=live`, `UNLINKED_UNIPILE_API_URL`, `UNLINKED_UNIPILE_API_KEY`, `UNLINKED_UNIPILE_DEMO_ACCOUNT_ID`, `UNLINKED_UNIPILE_TEST_ORIGIN`, and `UNLINKED_UNIPILE_ALLOWED_TARGET_SLUGS` only on an isolated authenticated stage after account entitlement and authorization have been checked. The target slug list should initially contain only the owner or one specifically consented target; an empty list denies all target lookups. The API URL must be an HTTPS Unipile API host; the origin is the exact HTTPS stage origin used for callbacks. `UNLINKED_UNIPILE_SYNC_SCOPE_VERIFIED=true` is an additional gate for creating a Hosted Auth link, after inspecting the provider's connection and sync effects. It is never inferred from a successful read call. Do not turn it on if a minimal connection scope cannot be established.

The pending Hosted Auth link expires after ten minutes. The v1 notification must return the random pending name and reach the exact notify URL, including its secret token. The server consumes the state once, retrieves the account by ID, requires a LinkedIn account with ready (`OK`) source status, and retrieves its owner profile before attaching its ID to the initiating tester. Only one connection transaction may be pending per tester; the final account assignment is rechecked synchronously after provider reads, including whether its callback is still the current transaction. The browser's success redirect changes no state. Starting a reconnect quarantines the existing source and invalidates its in-flight previews. Own-source reads resume only after the same account, ready source, and same verified LinkedIn owner ID are confirmed. A failed reconnect keeps the ownership reservation but leaves reads disabled. Both linked-account metadata and preview results live in process memory; server preview access expires after ten minutes or on Clear preview, which invalidates older in-flight reads. The browser also hides a displayed result at its ten-minute expiry. This intentionally requires a **single-instance test stage with process affinity**. A serverless multi-instance deployment will lose callbacks and state, so this state store must be replaced before any broader rollout. No Supabase migration or backend resume is part of this experiment.

Own connections use v1 `/api/v1/users/relations` with `limit=10` and decode each relation's v1 `member_id`. Target connections use one v1 Classic LinkedIn search with `connections_of=[target provider ID]` and `limit=10`, through the server-configured demo account; search result IDs are decoded separately. They are viewer-relative and may be incomplete. A missing or malformed page envelope is unavailable, never an empty network. The target preview is a single `/api/v1/users/{identifier}` read through that same viewer. The adapter has no message, invitation, import, sync, or arbitrary-route operation. It does not retry rate or challenge failures. Responses are reduced to basic names, headlines, IDs, and provider profile URLs; the target preview uses a canonical URL derived from the lookup input. Raw provider bodies are never logged.

Fixture verification: `npm test`, `npx tsc --noEmit`, focused ESLint, and `npm run build`. A local production server with synthetic Supabase URL/key returned HTTP 404 for page, API GET, and callback POST with the feature flag off; with the flag on and no browser session it returned HTTP 404 for page, API GET, and API POST. This checks only signed-out routing; no authenticated stage or browser-session integration was exercised. Live account status and profile reads are separately coordinated; no provider credential or call is needed for the fixture suite.

## Readiness receipt (2026-09-30)

The separate authorized account probe reported a v1 `api49` workspace with one LinkedIn source in `OK` status. It made three account-list requests, one own-profile request (HTTP 200), and one own-relations request at `limit=10` (HTTP 200, zero items, no cursor). This is an **empty own-connections outcome**, not evidence about any target's network. This implementation has made zero additional live provider requests. A live target-connections check remains unperformed because no specifically consented target URL or authenticated single-instance stage has been supplied. Hosted Auth linkage and provider sync effects also remain untested; the connection gate remains closed. The exact code SHA is recorded in the delivery status after commit.
