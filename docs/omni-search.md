# Header autocomplete

Every standalone-runtime page with the header search form enhances the existing GET `/network?q=…` form with people, company and navigation suggestions. The People directory (`/network`) hides the header field; its own toolbar search filters live (`docs/network-controls.md`). The layout uses the shared Public Sans typography, indigo tokens and profile avatars. The QR scan control stays beside search.

Focusing the field sends one `/search-suggestions?q=` warm-up (at most every 10 s), which starts loading the index and returns nothing. After two characters and a 100 ms pause, the browser requests `/search-suggestions?q=…`. While the request is pending, earlier rows that still contain every typed word stay visible. One stable status strip with 12px text sits immediately above the rows, showing “Searching people and companies…” for a pending lookup without earlier matches or “Updating suggestions…” when earlier matches remain. A visible searching indicator appears after 200 ms from eligible input, including the 100 ms debounce, avoiding spinner flashes on fast answers. After 1.5 seconds from eligible input, a still-pending lookup changes the strip to “Still searching… You can search all results.” The native form and “See all results” link remain available throughout the wait. `aria-busy` marks the result region separately. Reduced-motion users get the same static status cue. Answers already seen on the page are kept in memory only (at most 40, gone with the page) and redraw at once. No model runs for a keystroke.

Matching uses a prefix index (`src/utils/public-people/suggest-index.mjs`) built once per compiled snapshot, off the request path, so a keystroke visits only the postings of the words it can complete instead of scanning every profile. It covers names, headlines, companies, position titles and companies, schools and skills; about text and position descriptions are left to the full search. Every typed word must match: a name word completes from two letters and the last word (still being typed) from one; other text needs a whole word or four letters, except the last word, which completes from two (“northwind cap”). Word forms follow the directory (“investors” finds “investor”). People come back at most five, one per person: two published profiles with the same LinkedIn address are one suggestion (the member first), and namesakes stay separate with their headline. Order: every word in the name, then an exact or leading name match, then people the signed-in member knows, members before imported profiles, more connected people, then name order. Companies (at most three) complete against visible position company names, deduplicated without case.

**Membership.** Each suggestion with published membership evidence carries “On Unlinked” or “Not on Unlinked”, independently of “You know”. Unknown membership is left unlabelled; company and navigation suggestions do not acquire person badges.

**You know.** For a signed-in member, suggestions mark the people they are connected to — the same one-person identity as `/network` (`connectedProfiles`: own connection rows resolved to published profiles, plus public graph neighbours). The set is read in the background on the first request and kept 5 minutes per member (at most 500 members in memory); a keystroke never waits for it, so the very first suggestions after sign-in may come back unmarked. Signed-in responses are `no-store, private` with `Vary: Cookie`.

This browser-only endpoint accepts only one `q` parameter (up to 200 characters) and searches the published, whitelisted projection for signed-in and anonymous users alike. It never searches private imports or contact-card data; for a signed-in session it only reads that member's own connections to mark “You know”. Responses are `no-store`, and the browser stores no query history. Building the shared index reads the graph (about 0.7 s live), so suggestions reuse the last verified index: unchanged for 10 s, then for up to 60 s while one background read refreshes it (`suggestFreshMs` / `suggestStaleMs` on the reader; every other public read still checks the source each time). A failed refresh drops the kept index, so a revoked or unavailable publication fails closed on the next suggestion, and unavailable data never falls back to private imports. A hidden or removed profile can therefore appear in suggestions for up to 60 s; its profile page reads fresh. Its separate site-wide budget permits 600 requests per minute and eight in flight without using the full-page budget.

The progressively enhanced combobox supports Arrow Up/Down, Enter, Escape, Tab, click-away and Cmd/Ctrl+K. Suggestions remain native anchors: Cmd/Ctrl-click, middle-click and Shift-click retain browser link behavior. Keyboard Enter preserves the modifier keys for equivalent navigation. Selection stays on the same destination by `href` when refreshed results still contain it; otherwise it clears. Focus stays in the input while keyboard selection is announced through `aria-activedescendant`; status and errors are announced politely. IME composition suspends lookup. Autocorrect, autocapitalize and spellcheck are off. On phones and touch screens the field is 16px so iOS Safari and WKWebView do not zoom on focus. A tap on a suggestion keeps the panel open through the field's blur so the tap navigates. Requests are canceled on newer input, closing, blur and page exit, with a generation check to reject late responses and a six-second request timeout. The native form and “See all results” (the same URL the native form submits, with its hidden filters) remain available when suggestions fail. Without JavaScript the original search and QR links still work.

Verification: `node --test tests/omni-search.test.mjs tests/topbar-me-menu.test.mjs tests/shared-people-browser.test.mjs tests/profile-card.test.mjs`. Browser smoke checks should also cover mobile width, a slow response overtaken by a later query, offline fallback, company/profile navigation and native Enter submission.
